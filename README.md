# Завтра

Telegram-бот, который по продажам, техкартам и вечерним остаткам рассчитывает закупку ингредиентов на следующий день для небольшой точки общепита.

**Автор:** Бакиев Мехроб Мехрзодович. Проект для проектного семинара.

**Версия 0.1:** начальный MVP Telegram-бота. Сценарий: подключение точки → загрузка продаж и техкарт → остатки → рекомендация → ручная правка → подтверждение заказа. Сайт запланирован на следующий этап.

## Быстрый запуск

Нужен Python 3.12 или новее. Локально база SQLite создаётся автоматически; Docker для этого не нужен.

```bash
git clone https://github.com/MehrobBakiev/Zavtra.git
cd Zavtra
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
cp .env.example .env
```

Windows PowerShell: вместо `source` используйте `.venv\Scripts\Activate.ps1`.

### Проверить расчёт без Telegram

```bash
python -m zavtra demo
```

Команда создаёт отдельную демонстрационную точку, загружает синтетические продажи за последние 84 дня, три ингредиента и две техкарты, вводит остатки, рассчитывает закупку и сохраняет подтверждённый заказ. Она не обращается в Telegram. Каждый запуск создаёт новую демоточку; реальные данные не перезаписываются.

### Запустить Telegram-бота

1. Создайте бота у [@BotFather](https://t.me/BotFather) командой `/newbot`.
2. Вставьте полученный токен в локальный `.env`: `BOT_TOKEN=...`.
3. Создайте код подключения точки:

```bash
python -m zavtra invite --name "Моя шаурмичная"
```

4. Запустите бота:

```bash
python -m zavtra bot
```

5. Откройте личный чат со своим ботом и отправьте `/start КОД`, напечатанный командой `invite`.
6. Для первого знакомства отправьте `/demo`, затем `/stock`. Для демоданных подойдут остатки:

```text
Курица=2
Лаваш=60
Соус=0.5
```

7. После полного ввода бот покажет рекомендацию. Количества меняются кнопками; кнопка «Подтвердить заказ» сохраняет итоговый заказ.

Токен и коды подключения не нужно публиковать в GitHub или присылать в чат. `.env` и локальная база исключены из репозитория. Один токен бота должен использоваться одним polling-процессом.

Для второго сотрудника получите новый код к существующей точке:

```bash
python -m zavtra invite --point-id 1
```

Номер точки печатается при создании первого приглашения. Код одноразовый, действует 24 часа. До трёх аккаунтов на точку; в этой версии один аккаунт привязывается к одной точке. Данные доступны только в личном чате подключённым сотрудникам.

## Команды

| Команда | Действие |
| --- | --- |
| `/start КОД` | Подключить пользователя к точке |
| `/demo` | Загрузить синтетические данные в пустую точку |
| `/ingredients` | Загрузить/обновить ингредиенты CSV/XLSX |
| `/recipes` | Заменить техкарты файлом CSV/XLSX |
| `/sales` | Загрузить ежедневные продажи CSV/XLSX |
| `/templates` | Получить примеры файлов со свежими датами |
| `/stock` | Ввести вечерние остатки |
| `/recommend` | Пересчитать рекомендацию на завтра |
| `/forecast` | Показать прогноз порций из последнего расчёта |
| `/order` | Показать последний подтверждённый заказ |
| `/cancel`, `/help` | Отменить ввод, посмотреть помощь |

## Свои данные

Подключите отдельную пустую точку и загрузите файлы последовательно: `/ingredients`, `/recipes`, `/sales`. Пример файлов также можно создать в терминале:

```bash
python -m zavtra samples --output-dir data/samples
```

**Ингредиенты:** `name,unit,price,co,cu,step`. Единицы `кг`, `л`, `шт`; цена, Cu, Co и кратность положительные. Кратность по умолчанию 1; Co — закупочная цена. Пустой Cu допускается, но позиция требует ручного ввода количества перед подтверждением. Файл обновляет существующие названия и добавляет новые, максимум 10. Единицу уже существующего ингредиента менять нельзя.

**Техкарты:** `dish,ingredient,amount`. Норма положительная, в единице ингредиента. Название ингредиента должно совпадать со справочником. Файл полностью заменяет техкарты точки, до 100 блюд.

**Продажи:** `date,dish,quantity` или `дата,блюдо,количество`. Даты `ГГГГ-ММ-ДД`, `ДД.ММ.ГГГГ` или Excel-даты, порции — целые числа ≥0. Названия блюд должны совпадать с техкартами. CSV — UTF-8, разделитель запятая, точка с запятой или табуляция. Допустим XLSX, первый лист. Лимит файла 5 МБ, 50 000 строк, 100 блюд и 365 разных дат.

Продажи за даты загружаемого файла заменяются полностью. Повтор файла не удваивает продажи. Несколько строк одного блюда за день суммируются. **Каждая дата означает полный дневной отчёт:** если блюдо отсутствует в таком дне, его продажи считаются нулевыми. День без единой строки считается неизвестным; чтобы обозначить день с нулевыми продажами, включите строки с нулём.

Для прогноза нужны минимум 28 загруженных дней за последний год и полный отчёт за сегодняшний день. После первой загрузки продажи нужно обновлять ежедневно. Остатки вводятся в конце дня, когда продажи за него уже завершены; часовой пояс точки по умолчанию `Europe/Moscow`.

Если файл содержит ошибку, MVP показывает номер строки и не применяет весь файл. Это осознанное упрощение относительно частичного импорта из FR-01: оно предотвращает удаление корректных продаж из-за неполного нового отчёта.

## Расчёт

- Прогноз порций — среднее за последние восемь соответствующих дней недели; блюда без продаж последние 28 дней получают 0.
- Потребность — прогноз порций, умноженный на нормы ингредиента в техкартах.
- `CR = Cu / (Cu + Co)`, с ограничением 0.50–0.95.
- Запас определяется CR-квантилем относительных ошибок потребности на последовательном бэктесте за последние до 56 загруженных дней. Для каждого дня используются только предыдущие продажи, с минимум 28 днями обучения. Метод квантиля — линейный R-7.
- При менее 14 валидных ошибках используется +10% с пометкой «запас по умолчанию». Нулевые прогнозы исключаются из относительных ошибок.
- Из целевой потребности вычитается остаток; положительный заказ округляется вверх до кратности упаковки.

Рекомендованные и изменённые вручную количества сохраняются раздельно. До подтверждения изменение исходных данных делает старую рекомендацию неактуальной. После подтверждения заказ неизменяем; повторное подтверждение возвращает тот же заказ. Снимок продаж, техкарт, остатков и параметров позволяет воспроизвести расчёт.

Качество прогноза и целевое снижение списаний на 15% ещё не проверены на реальной точке. Демоданные показывают работу сценария.

## PostgreSQL и Docker

Для локального знакомства достаточно SQLite. Для серверного запуска подготовлен Compose с PostgreSQL 18. Заполните `BOT_TOKEN` и `POSTGRES_PASSWORD` в `.env`:

```bash
docker compose build
docker compose up -d db
docker compose run --rm bot python -m zavtra invite --name "Моя точка"
docker compose up -d bot
```

Команду `/start КОД` отправьте своему боту. PostgreSQL не публикует порт наружу; данные лежат в именованном томе. Перезапуск сохраняет базу. Резервное копирование для реального пилота нужно настроить отдельно.

## Проверки

```bash
python -m pytest -q
ruff check src tests
ruff format --check src tests
```

Интеграционный тест PostgreSQL запускается при заданном `TEST_POSTGRES_URL` и создаёт/удаляет только свою временную схему. GitHub Actions проверяет Python 3.12/3.14 и PostgreSQL. Тесты Telegram используют настоящий dispatcher aiogram и имитацию Telegram API; токен и сетевые запросы для них не нужны.

## Устройство

```text
src/zavtra/
  bot.py           команды, файлы, кнопки и диалоги Telegram
  service.py       сценарии подключения, импорта, остатков и заказа
  domain.py        прогноз, бэктест, квантили и формула закупки
  database.py      модели SQLAlchemy и конфигурация БД
  imports.py       чтение и проверка CSV/XLSX
  samples.py       генератор синтетических данных
  presentation.py  текстовые представления
  __main__.py      запуск бота и служебные команды
```

Общие расчёты не зависят от Telegram. Это позволит добавить API сайта к существующим сценариям. В текущей версии расчёт запускается по запросу пользователя; отдельного worker, HTTP API и сайта пока нет.

До полного MVP из SRS ещё нужны: расписание рекомендаций и повторы доставки, учёт списаний/нехваток, отчёт пилота, миграции схемы, резервное копирование и эксплуатационные проверки. Начальная схема создаётся через `create_all`; перед изменением схемы потребуется миграция. Диалог ввода после перезапуска начинается заново, уже сохранённые данные остаются в БД.
